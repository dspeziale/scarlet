# OBIETTIVO

Stiamo introducendo in azienda applicazioni containerizzate con Docker e dobbiamo portare in esercizio la prima applicazione, Scarlet.

Attualmente non abbiamo una conoscenza consolidata dell'ecosistema Docker e vogliamo quindi costruire una soluzione che renda il processo di sviluppo, deployment e gestione operativa il più possibile:

* semplice;
* robusto;
* ripetibile;
* sicuro;
* auditabile;
* comprensibile agli operatori;
* automatizzato dove opportuno;
* facilmente estendibile a più applicazioni.

Gli sviluppatori utilizzano GitHub.

Voglio che tu progetti e implementi una soluzione completa che permetta di gestire il ciclo:

GitHub
↓
build/test
↓
Docker image
↓
registry
↓
ambiente DEVELOPMENT
↓
approvazione/promozione
↓
ambiente PRODUCTION
↓
monitoraggio e gestione operativa

La soluzione deve essere realmente utilizzabile in produzione e non una semplice proof-of-concept.

---

# RUOLO

Agisci contemporaneamente come:

* Senior DevOps Engineer
* Platform Engineer
* Docker Engineer
* GitHub Actions Engineer
* Linux System Administrator
* Security Engineer
* Software Architect
* SRE

Devi prendere decisioni tecniche motivate.

Non limitarti a descrivere cosa fare: quando possibile, crea direttamente i file, gli script, le configurazioni e il codice necessari.

Non assumere che l'ambiente sia già correttamente configurato.

Prima analizza ciò che esiste nel repository e nell'ambiente.

---

# PRINCIPIO FONDAMENTALE

NON voglio un sistema inutilmente complesso.

Parti da una architettura pragmatica basata indicativamente su:

* Docker Engine
* Docker Compose
* GitHub
* GitHub Actions
* Container Registry
* Linux
* SSH/deployment agent
* reverse proxy quando necessario
* gestione dei secrets
* logging
* health check
* backup dove necessario

NON introdurre Kubernetes, OpenShift o altri orchestratori complessi salvo che dall'analisi emerga una necessità reale e documentata.

La soluzione deve essere facilmente comprensibile da un team che sta iniziando ad adottare Docker.

Preferisci:

1. semplicità;
2. affidabilità;
3. sicurezza;
4. automazione;
5. osservabilità;
6. estendibilità.

# ARCHITETTURA TARGET

Progetta una architettura nella quale:

## DEVELOPMENT

Gli sviluppatori lavorano normalmente su GitHub.

Un push/merge sul branch previsto deve attivare una pipeline.

La pipeline deve:

1. checkout del codice;
2. installazione dipendenze;
3. lint;
4. unit test;
5. eventuali integration test;
6. security scan delle dipendenze;
7. build Docker image;
8. Docker image vulnerability scan;
9. tagging immutabile dell'immagine;
10. push al registry;
11. deploy in DEVELOPMENT;
12. smoke test;
13. verifica health endpoint;
14. reporting dell'esito.

---

# VERSIONING DELLE IMMAGINI

Non utilizzare solamente tag come:

latest

Il sistema deve utilizzare tag immutabili.

Preferenza:

* Git SHA
* eventualmente semantic version
* eventualmente build number

Esempio:

myapp:git-a1b2c3d4

oppure:

myapp:v1.4.2

L'ambiente deve poter sapere esattamente quale immagine sta eseguendo.

Deve essere possibile rispondere facilmente alla domanda:

"Quale versione dell'applicazione è attualmente in produzione?"

---

# REGISTRY

Progetta l'utilizzo di un Docker/OCI registry.

Se possibile, usa GitHub Container Registry (GHCR), salvo motivazioni tecniche per scegliere un registry diverso.

Documenta:

* autenticazione;
* naming;
* retention;
* gestione immagini;
* access control;
* vulnerability scanning;
* lifecycle.

Non utilizzare credenziali statiche inserite nei repository.

---

# DEVELOPMENT DEPLOYMENT

Prevedi un meccanismo robusto per fare deployment sul server di sviluppo.

Preferenza iniziale:

GitHub Actions
↓
SSH sicuro
↓
server DEVELOPMENT
↓
docker compose pull
↓
docker compose up -d
↓
health check
↓
smoke test

Ma valuta anche alternative.

La soluzione scelta deve essere motivata.

Sul server non deve essere necessario compilare l'applicazione.

Il server deve scaricare una immagine già costruita e verificata.

---

# PRODUCTION DEPLOYMENT

La produzione deve essere separata dallo sviluppo.

NON deve essere possibile che un semplice push provochi accidentalmente il deployment in produzione.

Prevedi un processo esplicito di promozione.

Ad esempio:

GitHub
↓
build image
↓
development
↓
test
↓
approval
↓
production

La produzione deve utilizzare la STESSA immagine già validata in development.

NON deve essere effettuato un nuovo build per la produzione.

Questo è importante.

Voglio un principio:

"build once, promote the same artifact"

Prevedi quindi un workflow GitHub Actions appropriato con:

* environments;
* protection rules;
* manual approval quando appropriato;
* secrets separati;
* deployment history;
* possibilità di rollback.

---

# STRATEGIA DI DEPLOYMENT

Progetta un deployment inizialmente semplice e affidabile.

Valuta almeno:

* recreate;
* rolling;
* blue/green;
* canary.

Per una prima implementazione scegli la soluzione più appropriata rispetto all'infrastruttura disponibile.

Non complicare inutilmente il sistema.

Se utilizzi Docker Compose, considera attentamente:

* downtime;
* health check;
* dipendenze;
* graceful shutdown;
* restart policy;
* gestione delle migrazioni DB;
* rollback.

Documenta i trade-off.

# GESTIONE OPERATIVA

Questa parte è fondamentale.

Voglio una interfaccia chiara per gli operatori.

Deve essere possibile eseguire almeno:

* status;
* start;
* stop;
* restart;
* deploy;
* rollback;
* logs;
* health;
* version;
* update/pull;
* diagnostica.

Progetta una CLI semplice, ad esempio:

appctl status
appctl start
appctl stop
appctl restart
appctl deploy
appctl rollback
appctl logs
appctl health
appctl version
appctl doctor

Valuta se sia meglio:

* Bash;
* Python;
* Go.

Scegli tu in base a robustezza e semplicità di distribuzione.

L'interfaccia deve essere estremamente comprensibile.

Esempio:

$ appctl status

Environment: production
Version: 1.4.2

Status: RUNNING
Health: HEALTHY
Started: 2026-09-30 08:42:11
Container: myapp

Non voglio output inutilmente tecnico per le operazioni normali.

Per le operazioni diagnostiche deve invece essere possibile ottenere informazioni dettagliate.

# WEB UI

Valuta se sia utile aggiungere una piccola Web UI per gli operatori.

Se la proponi, deve essere:

* semplice;
* sicura;
* responsive;
* molto chiara;
* orientata alle operazioni;
* senza framework inutilmente pesanti.

La UI dovrebbe mostrare:

Dashboard

* applicazione;
* ambiente;
* versione;
* stato container;
* health;
* uptime;
* ultima operazione;
* ultimo deployment;
* commit;
* immagine Docker.

Azioni:

* Start
* Stop
* Restart
* Deploy
* Rollback
* Logs

Se implementi la UI:

* autenticazione obbligatoria;
* autorizzazione;
* audit log;
* CSRF protection se applicabile;
* rate limiting dove opportuno;
* nessuna esposizione pubblica non necessaria;
* nessuna possibilità di eseguire comandi arbitrari.

NON creare una "Docker management UI" generica che consenta agli utenti di eseguire qualsiasi container/comando.

La UI deve esporre solamente le operazioni applicative consentite.

Se ritieni che una Web UI sia prematura, implementa inizialmente CLI + documentazione, ma documenta come evolvere successivamente verso una UI.

---

# LOGGING

La soluzione deve gestire correttamente i log.

Distinguere:

1. application logs;
2. container logs;
3. deployment logs;
4. audit logs;
5. system logs.

Prevedi:

appctl logs

e possibilità di:

appctl logs --follow

appctl logs --since 1h

appctl logs --tail 200

I log devono essere accessibili agli operatori senza entrare manualmente nei container.

Non utilizzare log file interni al container come meccanismo principale se Docker stdout/stderr è sufficiente.

Documenta retention e rotazione.

Evita che un container possa riempire il filesystem.

---

# HEALTH CHECK

Ogni applicazione deve avere health check.

Preferenza:

/health

e, se appropriato:

/ready

Distinguere:

* l'applicazione è avviata;
* l'applicazione è viva;
* l'applicazione è pronta a ricevere traffico;
* dipendenze critiche disponibili.

Il deployment deve verificare la health dopo il deploy.

Se la health check fallisce:

* il deployment deve risultare FAILED;
* deve essere disponibile una diagnostica;
* deve essere possibile rollback.

---

# DATABASE

Se l'applicazione utilizza un database:

NON inserire automaticamente il database nel medesimo Compose file senza prima valutare le conseguenze.

Analizza:

* database esterno;
* database containerizzato;
* backup;
* persistence;
* migration;
* rollback schema;
* compatibilità versione.

Le migrazioni devono essere gestite esplicitamente.

Non assumere che:

docker compose up -d

sia sufficiente per una migrazione DB sicura.

Documenta una strategia.

---

# SECRETS

NON salvare secrets:

* nel repository;
* nel Dockerfile;
* nelle immagini;
* nei log;
* nei file YAML versionati.

Analizza opzioni:

* GitHub Actions Secrets;
* GitHub Environments;
* secret manager;
* Docker secrets;
* file protetti sul server.

Per la prima versione scegli la soluzione più semplice che garantisca un livello di sicurezza adeguato.

I secrets di DEVELOPMENT e PRODUCTION devono essere distinti.

Non usare mai credenziali production nei workflow development.

---

# SICUREZZA SERVER

Definisci una baseline.

Considera almeno:

* Linux aggiornato;
* Docker Engine aggiornato;
* SSH key authentication;
* no password authentication;
* firewall;
* porte minime necessarie;
* Docker socket protection;
* utenti non-root;
* container non-root quando possibile;
* read-only filesystem quando possibile;
* capabilities minimizzate;
* resource limits;
* ulimits;
* restart policies;
* image vulnerability scanning;
* dependency scanning;
* secret scanning;
* audit.

Il container NON deve girare come root se non necessario.

Il Docker socket non deve essere esposto alla rete.

Se la UI deve interagire con Docker, non esporre direttamente il Docker socket alla UI pubblica.

---

# DOCKERFILE

Verifica e, se necessario, migliora il Dockerfile.

Deve seguire best practice:

* multi-stage build;
* immagine base minimale;
* versioni fissate;
* utente non-root;
* .dockerignore;
* nessun secret;
* healthcheck quando appropriato;
* layer efficienti;
* cache efficace.

Valuta immagini:

* Alpine;
* Debian slim;
* distroless;

ma scegli in base alle reali esigenze dell'applicazione.

Non utilizzare Alpine automaticamente.

---

# DOCKER COMPOSE

Prevedi una struttura chiara.

Ad esempio:

deploy/
compose.yaml
compose.dev.yaml
compose.prod.yaml
.env.example

oppure una struttura migliore se la ritieni necessaria.

Separare chiaramente:

* configurazione comune;
* development;
* production.

Non duplicare configurazioni inutilmente.

---

# SYSTEMD

Valuta se Docker Compose debba essere gestito da systemd.

La soluzione deve garantire che dopo reboot del server l'applicazione ritorni correttamente online.

Valuta:

* Docker restart policies;
* systemd;
* dipendenze;
* startup ordering.

Scegli e documenta.

---

# BACKUP

Individua cosa deve essere salvato.

Considera:

* database;
* volumi persistenti;
* configurazioni;
* secrets/configuration;
* deployment metadata;
* audit logs.

Non implementare backup fittizi.

Se l'infrastruttura di backup non è disponibile, prepara:

* struttura;
* script;
* retention policy;
* documentazione;
* TODO espliciti.

---

# ROLLBACK

Il rollback deve essere una funzione di primo livello.

Deve essere possibile sapere:

Versione attuale:
v1.4.2

Versione precedente:
v1.4.1

Eseguire:

appctl rollback

oppure:

appctl rollback v1.4.1

Il rollback deve utilizzare immagini già esistenti nel registry.

Non ricompilare.

Deve essere documentato cosa succede alle eventuali migrazioni database.

---

# AUDIT

Ogni operazione significativa deve essere tracciabile.

Almeno:

* chi;
* quando;
* cosa;
* ambiente;
* versione;
* risultato.

Esempio:

2026-09-30 10:32
user: mario
environment: production
action: deploy
version: v1.4.2
result: success

L'audit log non deve essere modificabile tramite le normali funzioni operative.

# CI/CD GITHUB ACTIONS

Crea workflow separati e comprensibili.

Ad esempio:

.github/workflows/ci.yml
.github/workflows/deploy-development.yml
.github/workflows/promote-production.yml

Ma scegli la struttura migliore.

Il workflow CI deve eseguire:

* checkout;
* test;
* lint;
* security checks;
* build;
* scan;
* push registry.

Il deployment deve essere separato dal build quando appropriato.

Usa GitHub Environments:

development
production

Production deve avere protection rules.

Non utilizzare PAT personali se può essere evitato.

Preferisci OIDC/GitHub-native authentication quando supportato.

# CONCORRENZA

# GIT

Lavora con modifiche piccole e comprensibili.

Non cancellare codice esistente senza motivo.

Non fare refactoring massivi se non necessari.

Prima di modificare file esistenti, comprendine il ruolo.

Mantieni compatibilità con l'applicazione.

---

# GESTIONE DELLE INFORMAZIONI MANCANTI

Quando trovi informazioni mancanti:

NON inventarle.

Classificale come:

* BLOCKER
* REQUIRED
* RECOMMENDED
* ASSUMPTION

Se puoi procedere in sicurezza con un'ASSUMPTION, fallo e documentala.

Se invece serve necessariamente una decisione umana, fermati prima della fase interessata e chiedimi l'informazione.

# CRITERI DI ACCETTAZIONE

Considera il lavoro completato solamente quando è possibile dimostrare almeno questo scenario end-to-end:

1. developer fa push su GitHub;
2. GitHub Actions esegue test;
3. viene costruita una Docker image;
4. l'image viene scansionata;
5. l'image viene pubblicata sul registry;
6. viene effettuato deployment DEVELOPMENT;
7. l'applicazione risulta HEALTHY;
8. viene eseguito smoke test;
9. un operatore approva/promuove la versione;
10. la stessa identica image viene deployata in PRODUCTION;
11. PRODUCTION risulta HEALTHY;
12. `appctl status` mostra versione e commit corretti;
13. `appctl logs` mostra i log;
14. `appctl restart` funziona;
15. viene simulato un deployment fallito;
16. viene eseguito rollback;
17. l'applicazione torna alla versione precedente;
18. l'intera procedura è documentata.

# REQUISITO FINALE

Non voglio solamente "un sistema che funziona".

Voglio una piccola piattaforma DevOps interna, inizialmente semplice, che possa diventare nel tempo lo standard aziendale per le applicazioni Docker.

Deve essere:

* comprensibile;
* ripetibile;
* sicura;
* verificabile;
* documentata;
* manutenibile;
* estendibile.

Quando devi scegliere tra una soluzione molto sofisticata e una soluzione più semplice che soddisfa gli stessi requisiti, scegli quella semplice.

Quando una scelta comporta un compromesso, esplicitalo.

Quando una soluzione può creare un rischio operativo, evidenzialo.

Quando puoi automatizzare un'attività ripetitiva senza aumentare significativamente la complessità, automatizzala.

Il risultato finale deve essere qualcosa che un team IT possa realmente adottare e utilizzare in esercizio.
