1. Cos'è SCARLET

SCARLET è la console centrale con cui il team operativo gestisce il ciclo di vita delle applicazioni installate sui server Oracle Linux aziendali che usano Docker, Podman o Kubernetes. Da un'unica interfaccia web si registrano i server, si caricano i pacchetti di rilascio preparati dai team di sviluppo, si eseguono i deployment e si controllano le applicazioni (avvio, arresto, riavvio, stato, log, health check, rollback) senza mai aprire una sessione SSH a mano.

SCARLET si collega ai server via SSH con credenziali cifrate, esegue soltanto comandi controllati e registra ogni azione nel registro di audit. Le differenze tra Docker, Podman e Kubernetes sono gestite internamente: l'operatore vede sempre la stessa interfaccia.

Questa guida è pensata per amministratori e operatori con conoscenze limitate dei container. Le procedure passo-passo con precondizioni, errori e ripristino sono nel documento docs/RUNBOOK.md; il contratto tecnico per i team di sviluppo è in docs/APPLICATION_RELEASE_CONTRACT.md.

2. Concetti fondamentali

TermineSignificato
HostUn server remoto Oracle Linux raggiunto via SSH. Ha un ambiente (DEV o PROD), un runtime (Docker, Podman, Kubernetes) e una credenziale SSH cifrata.
AmbienteDEV sviluppo/test; PROD produzione. Le operazioni in PROD richiedono permessi aggiuntivi, un motivo e una frase di conferma digitata.
ApplicazioneUn'applicazione di business (es. customer-api) con il suo runtime, le regole sui target consentiti e i parametri di health check.
Versione / ReleaseUna versione immutabile dell'applicazione (es. 2.5.0), creata dal caricamento di un pacchetto valido. Non può essere modificata: per cambiare qualcosa si pubblica una nuova versione.
PacchettoFile nome-versione.scarlet.tar.gz contenente manifest.yaml e i file dell'applicazione. Viene validato prima di diventare una release.
IstanzaLa combinazione applicazione + host. Per ogni istanza SCARLET conserva lo stato desiderato (cosa ha chiesto l'operatore) e lo stato reale (cosa osserva sul server).
DeploymentL'operazione che porta una versione su un host: validazione, trasferimento, installazione, attivazione, avvio, health check. Ogni passo è registrato.
OperazioneUn'azione sul ciclo di vita (START, STOP, RESTART, STATUS, HEALTH, LOGS, VERSION) eseguita in background e tracciata con un riferimento OP-….
DriftDifferenza tra stato desiderato e stato reale (es. versione diversa, container fermo inaspettatamente). Viene rilevata periodicamente e segnalata.
RollbackRitorno alla release precedente, con riattivazione, riavvio e health check. È un'operazione tracciata come un deployment di tipo ROLLBACK.

3. Cosa installare su ogni macchina

SCARLET è senza agente: sui server gestiti non si installa nessun componente SCARLET, basta SSH e il runtime dei container. Le macchine coinvolte sono quattro tipi.

MacchinaDa installareNote
Server SCARLET
una sola macchina centrale, Oracle Linux 8.8+/9
  • podman + podman-compose (oppure Docker Engine + plugin compose)
  • git o il pacchetto del repository, firewalld, policycoreutils-python-utils (SELinux)
  • certificato TLS (CA interna o Let's Encrypt)
 PostgreSQL 16, Redis 7, nginx e l'applicazione girano come container del compose (deployment/docker-compose.yml). Requisiti: 2–4 vCPU, 4–8 GB RAM, 40–100 GB disco. Dettagli in docs/installation.md. Nessun Python da installare sul sistema: è dentro l'immagine.
Server di destinazione
ogni Oracle Linux su cui girano le applicazioni
  • openssh-server (già presente)
  • un runtime: podman (consigliato) oppure Docker Engine, oppure kubectl configurato per il cluster
  • utilità: tar gzip coreutils curl nmap-ncat (dnf install -y podman tar gzip curl nmap-ncat)
  • un utente Linux dedicato (es. scarlet) con la chiave pubblica di SCARLET e accesso in scrittura a /opt/scarlet; per Podman rootless loginctl enable-linger
 Nessun agente, nessun Python, nessun sudo. Le immagini arrivano dal registry aziendale raggiungibile dall'host oppure dentro il pacchetto (image.archive) per host isolati. Aprire sul firewall la porta SSH verso il server SCARLET e le porte delle applicazioni.
PC degli operatori Solo un browser moderno (Chrome, Edge, Firefox). Nessuna installazione: tutto avviene dalla console web. Chi usa l'API da script ha bisogno soltanto di curl o di qualsiasi client HTTP e di un token personale.
PC / pipeline del team applicativo
chi produce i pacchetti
  • il proprio strumento di build dell'immagine (Docker/Podman) e docker save se l'immagine viaggia nel pacchetto
  • Python 3.12+ con il repository SCARLET per scripts/build-scarlet-package.py (pip install -r requirements/base.txt), oppure qualunque tool che produca un tar.gz conforme al contratto
 Il builder valida il pacchetto con le stesse regole dell'upload, così gli errori emergono prima di consegnarlo alle operations. Il caricamento può essere automatizzato via API con un token.
PC di sviluppo di SCARLET
solo per chi modifica SCARLET stesso		 Docker Desktop o Podman Desktop (con compose), Python 3.12+, git. docker compose --profile dev up -d --build avvia tutto, compresi i due server simulati mockhost (DEV) e mockhost-prod (PROD). Vedi docs/development.md.
Versioni minime: Podman 4.x (5.x consigliato), Docker Engine 24+, Kubernetes 1.27+, PostgreSQL 13+ (16 nel compose), Redis 6+ (7 nel compose). SELinux può e deve restare in modalità enforcing: i volumi sono etichettati automaticamente (:Z).

Gli health check delle applicazioni vengono eseguiti dal server di destinazione stesso su 127.0.0.1: non serve alcun flusso da SCARLET verso le porte applicative. I server di destinazione non devono mai raggiungere SCARLET (nessun agente, nessuna callback). PostgreSQL, Redis e gunicorn parlano solo nella rete interna dei container.

4. Esempio completo 1 — Da zero a una macchina online

Questo esempio parte da una installazione SCARLET vuota e arriva a un'applicazione in esecuzione su un server, seguendo esattamente l'ordine con cui lavorereste in produzione. Tempo stimato: 30–40 minuti. Ruolo necessario: ADMIN (per host, credenziali e fingerprint) e OPERATOR per il deployment. Dove non avete ancora un server reale, il passo 0 spiega come usare il server simulato incluso in SCARLET.

Passo 0 — Cosa serve

  • SCARLET avviato (docker compose --profile dev up -d --build) e raggiungibile, es. http://localhost:8090; credenziali dell'utente admin (password iniziale da SCARLET_INITIAL_ADMIN_PASSWORD, cambiata al primo accesso).
  • Un server Oracle Linux 8/9 raggiungibile via SSH dal server SCARLET. In alternativa il profilo dev di Docker Compose avvia due server simulati: mockhost (da registrare come DEV) e mockhost-prod (da registrare come PROD), entrambi con utente scarlet, password scarlet-dev, Podman già installato, raggiungibili dai container SCARLET con quei nomi (dall'esterno sulle porte 2222 e 2223).
  • Il pacchetto di esempio examples/podman-app del repository (applicazione customer-api, immagine nginx).

Passo 1 — Preparare il server (una volta sola, come root sul server)

sudo dnf install -y podman tar gzip nmap-ncat curl
sudo useradd -m scarlet
sudo mkdir -p /opt/scarlet && sudo chown scarlet:scarlet /opt/scarlet
sudo loginctl enable-linger scarlet
sudo firewall-cmd --permanent --add-service=ssh && sudo firewall-cmd --reload
# porta dell'applicazione (nell'esempio 8080)
sudo firewall-cmd --permanent --add-port=8080/tcp && sudo firewall-cmd --reload

Generare sul server SCARLET (o sul vostro PC) una coppia di chiavi dedicata e installare la chiave pubblica sul server di destinazione:

ssh-keygen -t ed25519 -N "" -f scarlet_ed25519 -C "scarlet@scarlet-server"
ssh-copy-id -i scarlet_ed25519.pub scarlet@srv-app-01.azienda.it     # oppure copiare a mano in ~scarlet/.ssh/authorized_keys
ssh -i scarlet_ed25519 scarlet@srv-app-01.azienda.it 'podman --version && touch /opt/scarlet/.ok'   # verifica

Leggere e annotare il fingerprint della chiave host del server (servirà al passo 4):

ssh scarlet@srv-app-01.azienda.it 'ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub'
# 256 SHA256:Ab3dEf...   root@srv-app-01 (ED25519)
Con il server simulato questo passo è già fatto: utente, Podman e permessi sono predisposti dall'immagine docker/mockhost. Si usa l'autenticazione a password (scarlet-dev) solo perché è un ambiente di prova.

Passo 2 — Registrare l'host in SCARLET

  1. Login come admin → Infrastructure → Hosts → New host.
  2. Compilare: Name srv-app-01 (o mockhost), Hostname srv-app-01.azienda.it (o mockhost), SSH username scarlet, porta 22, Environment DEV, Runtime PODMAN.
  3. Create host. Stato: UNKNOWN, chiave host: UNKNOWN.

Passo 3 — Inserire la credenziale

  1. Security → Credentials → riga dell'host → Add / rotate.
  2. Tipo SSH private key, incollare il contenuto di scarlet_ed25519 (per il server simulato: tipo SSH password, valore scarlet-dev).
  3. Save credential. La credenziale compare come ACTIVE con il fingerprint della chiave; il valore non sarà mai più visibile.

Passo 4 — Approvare il fingerprint del server

  1. Pagina dell'host → Scan host key. Compare il riquadro giallo "SSH host key pending approval" con il fingerprint SHA256:….
  2. Confrontarlo con quello annotato al passo 1: deve coincidere carattere per carattere.
  3. Approve fingerprint → digitare il fingerprint → conferma. Stato chiave: APPROVED.

Se SCARLET è in modalità tofu (solo sviluppo) il passo è automatico al primo Test connection.

Passo 5 — Test connessione e Discover

Test connection → finestra con esito SUCCESS ONLINE, utente remoto scarlet, latenza in ms. Poi Discover: esempio di risultato reale sul server simulato:

OS            Oracle Linux Server 9.6
Kernel / arch x86_64        CPU 8      Memory 7.4 GB   Disk 120 GB free su /
SELinux       (assente nel simulatore; "Enforcing" su un server reale)
Runtimes      PODMAN  ONLINE  5.8.2 rootful
              DOCKER  OFFLINE docker not found in PATH
              KUBERNETES OFFLINE kubectl not found

La pagina dell'host mostra ora sistema operativo, risorse e capacità rilevate. Se il runtime era NONE, premere Edit e impostarlo a PODMAN.

Passo 6 — Registrare l'applicazione

Applications → New application: Name Customer API, Code customer-api, Runtime PODMAN, Default port 8080, Health check HTTP path / porta 8080, Allowed environments DEV e PROD, Allow deployment hooks attivo (il pacchetto di esempio contiene script di hook). Create application.

Passo 7 — Costruire e caricare il pacchetto

Dal repository SCARLET, sul PC dell'operatore o del team applicativo:

python scripts/build-scarlet-package.py --source examples/podman-app --version 1.0.0 --output dist/
package : dist/customer-api-1.0.0.scarlet.tar.gz
app     : customer-api 1.0.0 (podman)
sha256  : 57c6a9d0…

Applications → Packages → Upload: trascinare il file, Upload & validate → VALID, "Release created". Il manifest dichiara il segreto DB_PASSWORD: senza configurarlo il pre-flight fallirà (voluto).

Passo 8 — Configurare il segreto richiesto

Applications → Customer API → Configuration → scheda DEV → Add entry: Key DB_PASSWORD, tipo SECRET, valore a scelta, Save. La voce appare mascherata (••••••••); nasce la versione di configurazione v1.

Passo 9 — Deployment con il wizard

  1. Operations → Deployments → New deployment → Application customer-api → Version 1.0.0 → Target srv-app-01 → Environment (DEV, strategia SEQUENTIAL) → Next.
  2. Pre-flight: tutte le voci PASS (SSH, chiave, credenziale, runtime PODMAN 5.8.2, disco, memoria, porte 8080 libera, pacchetto verificato, segreti configurati, nessun conflitto).
  3. Confirmation: Reason prima installazione → Deploy.
  4. Execution: i passi si completano in sequenza; esito reale registrato sul server simulato:
[SUCCESS] Validate package            [SUCCESS] Check target             [SUCCESS] Prepare remote layout
[SUCCESS] Transfer package            [SUCCESS] Verify checksum          [SUCCESS] Extract release
[SUCCESS] Render configuration        [SUCCESS] Run pre-deploy hooks     [SUCCESS] Run migration hooks
[SUCCESS] Install release (podman pull docker.io/library/nginx:1.27-alpine)
[SUCCESS] Activate release (current -> releases/1.0.0)
[SUCCESS] Start application (podman run -d --name customer-api …)
[SUCCESS] Health check (HTTP 200 su http://127.0.0.1:8080/)
[SUCCESS] Run post-deploy hooks       [SUCCESS] Finalize                 [SUCCESS] Clean staging
SUCCESS — Version 1.0.0 deployed successfully.

La macchina è online: Applications → Customer API mostra l'istanza su srv-app-01 con desiderato 1.0.0/RUNNING, reale 1.0.0/RUNNING, health HEALTHY, "in sync". Dal server: curl http://srv-app-01.azienda.it:8080/ risponde con la pagina nginx.

Passo 10 — Esercizio quotidiano

  • Status → RUNNING, version 1.0.0, Drift: none.
  • Logs → ultime righe di podman logs customer-api, es. "GET / HTTP/1.1" 200 615 "-" "curl/7.76.1" generata dall'health check.
  • Stop → STOPPED; Start → STARTED; Restart → RESTARTED.
  • Seconda versione: build-scarlet-package.py --version 1.1.0, upload, deploy → l'istanza mostra current 1.1.0 e previous 1.0.0. Rollback → deployment RBK-… SUCCESS, current torna 1.0.0. Tutto è consultabile in Audit → Audit Log.

5. Esempio completo 2 — TEXA ARES 118 in DEV e in PROD

TEXA ARES 118 è una webapp Flask reale dell'azienda (telematica di flotta) oggi distribuita con uno script PowerShell (build_and_deploy.ps1) che costruisce l'immagine Docker, la esporta in texa_ares_webapp-X.Y.Z.tar.gz, la copia via SSH sull'host e riavvia il container texa_ares_webapp sulla porta 5100 con sudo docker, leggendo la configurazione da ~/texa_deploy/texa.dev.env o texa.prod.env. Questo esempio mostra come lo stesso rilascio viene gestito da SCARLET, con un ambiente DEV e uno PROD. Il progetto originale non è stato modificato: tutto il materiale SCARLET vive nella copia di lavoro scarlet/work/texa-ares.

1. Il pacchetto SCARLET di TEXA

Il team applicativo continua a produrre l'immagine come oggi; cambia solo il confezionamento finale. La copia di lavoro contiene:

work/texa-ares/
├── manifest.yaml                 contratto SCARLET (sotto)
├── application/image.tar.gz      copia di texa/deploy_package/texa_ares_webapp-1.0.1.tar.gz (docker save)
├── config/texa.env               chiavi NON segrete (TEXA_ENV, TEXA_CLIENT_ID, EVENTHUB_CONSUMER_GROUP, …)
└── README.md                     come rigenerare il pacchetto a ogni release

Il manifest traduce deploy.sh e docker-compose.yml nel contratto SCARLET:

manifest_version: 1
application: texa-ares
version: 1.0.1
runtime: podman                          # sugli host con Docker l'applicazione consente anche DOCKER
image:
  name: webapp-webapp                    # tag prodotto da build_and_deploy.ps1
  tag: 1.0.1
  archive: application/image.tar.gz      # immagine dentro il pacchetto: nessun registry sull'host
  pull_policy: never
ports: [{ container: 5100, host: 5100 }]
environment: { FLASK_ENV: production, PYTHONUNBUFFERED: "1" }
environment_files: [config/texa.env]
secrets: [SECRET_KEY, TEXA_CLIENT_SECRET, EVENTHUB_CONNECTION_STRING, DATABASE_URL]
volumes: [{ name: status, mount: /app/status, shared: data }]
healthcheck: { type: tcp, port: 5100, retries: 10, interval: 6 }
deployment: { strategy: recreate, restart_policy: always, stop_grace_period: 15 }
resources: { cpu: "1", memory: 1Gi }

Punti chiave: nessun segreto nel pacchetto (i quattro valori sensibili di texa.*.env diventano voci SECRET in SCARLET, distinte per ambiente); l'immagine viaggia dentro il pacchetto (200 MB) perché gli host non hanno accesso a un registry; l'health check è TCP perché la home page richiede Oracle.

2. Registrazione in SCARLET

  1. Hosts: l'host DEV (nell'esempio il simulato mockhost; in azienda bc-test-ws-dkr50) come DEV, e l'host PROD (mockhost-prod; in azienda il server di produzione) come PROD, entrambi runtime PODMAN o DOCKER a seconda dell'host, con credenziale e fingerprint approvato (Esempio completo 1, passi 2–5). Nota: SCARLET non usa sudo; l'utente SSH deve poter eseguire podman/docker direttamente (gruppo docker o Podman rootless).
  2. Applications → New application: Name TEXA ARES 118, Code texa-ares, Runtime PODMAN, Allowed runtimes PODMAN + DOCKER, Allowed environments DEV + PROD, porta 5100, health check TCP 5100.

Configuration → PROD: gli stessi nomi con i valori di texa.prod.env (consumer group diverso, come richiede TEXA). In questo esempio sono stati usati valori fittizi: la webapp parte ma non raggiunge Oracle/TEXA.

4. Promozione in PROD

Stessa release, host PROD. Le differenze rispetto a DEV sono tutte controlli di sicurezza:

  • servono i permessi prod.deployment.execute (ruolo PROD_OPERATOR o ADMIN);
  • il campo Reason è obbligatorio (es. CHG-0001 go-live TEXA);
  • va digitata la frase {{ prod_phrase }}; senza, la richiesta è rifiutata con PRODUCTION_SAFETY (verificato: 403 PRODUCTION_SAFETY — "Production confirmation failed. Type exactly: DEPLOY TO PROD");
  • se l'ambiente PROD richiede approvazione, il deployment resta PENDING APPROVAL finché un secondo utente non approva (capitolo Approvazione a due persone).

Esito reale del deployment PROD:

DEP-20260913-000003 SUCCESS — 13 passi, 22 secondi complessivi
Install release 11.5 s (podman load) · Start application 0.6 s · Health check 6.1 s (TCP 5100)

Al termine Applications → TEXA ARES 118 mostra due istanze: mockhost (DEV) RUNNING 1.0.1 HEALTHY · mockhost-prod (PROD) RUNNING 1.0.1 HEALTHY. Il pannello Health le tiene sotto controllo ogni 10 minuti; il reconciler segnala DRIFT se qualcuno fermasse o sostituisse il container a mano sull'host.

5. Ciclo di vita successivo

  • Nuova release (es. 1.0.2): il team aggiorna APP_VERSION, costruisce l'immagine come oggi, copia il nuovo tar.gz in work/texa-ares/application/image.tar.gz, esegue il builder con --version 1.0.2, carica il pacchetto. Deploy prima in DEV, poi in PROD con conferma.
  • Rollback in PROD: istanza → Rollback → motivo → ROLLBACK PROD → SCARLET riattiva releases/1.0.1 (già sull'host, nessun trasferimento) e riavvia; equivale all'attuale ./deploy.sh prod 1.0.1 ma tracciato e senza SSH manuale.
  • Cambio di un segreto (es. rotazione TEXA_CLIENT_SECRET): Configuration → PROD → modifica della voce SECRET → Restart dell'istanza (rigenera scarlet.env al prossimo deploy; per applicarlo subito eseguire un nuovo deployment della stessa versione).
  • Log e stato: Monitoring → Logs con l'istanza texa-ares @ mockhost-prod; Status mostra versione e drift.

6. Accesso, ruoli e permessi

Si accede dalla pagina di login con nome utente e password. Al primo accesso (o dopo un reset da parte di un amministratore) viene richiesto di cambiare la password: minimo 12 caratteri con almeno tre tipi tra minuscole, maiuscole, cifre e simboli. Dopo 10 tentativi errati l'account viene bloccato per 15 minuti.

RuoloCosa può fare
VIEWERSola lettura: dashboard, host, applicazioni, deployment, log, health.
AUDITORCome VIEWER più consultazione ed esportazione del registro di audit.
OPERATOROpera sugli host DEV: caricamento pacchetti, deployment, start/stop/restart, rollback, configurazione. Sugli host PROD è in sola lettura.
PROD_OPERATORCome OPERATOR ma anche su PROD; può approvare deployment di produzione richiesti da altri.
ADMINTutto, inclusi utenti, ruoli, credenziali, approvazione fingerprint, impostazioni di sistema.

I pulsanti non disponibili per il proprio ruolo appaiono disabilitati con il permesso mancante nel suggerimento; in ogni caso il controllo è applicato dal server, non solo dall'interfaccia.

Dal menu utente (in alto a destra) si cambia la password, si gestiscono i token API personali e si esce dalla sessione. La sessione dura 8 ore.

7. Dashboard

La pagina iniziale riassume lo stato della piattaforma:

  • Riquadri: numero di host (DEV/PROD), applicazioni, deployment di oggi e riusciti, guasti (deployment falliti, applicazioni in errore, health check non superati).
  • Grafico dei deployment degli ultimi 14 giorni (riusciti/falliti).
  • Deployment e operazioni recenti con collegamento al dettaglio.
  • Istanze: quante applicazioni sono in esecuzione, ferme, in errore.
  • Host con problemi: host non raggiungibili o con fingerprint SSH da approvare.
  • Unhealthy / drift: istanze con health check fallito o con differenze tra stato desiderato e reale.
  • Eventi di sicurezza non ancora presi in carico e ultimi eventi di audit.

L'icona a campanella mostra le notifiche non lette; il contatore indica le operazioni in corso in questo momento.

8. Host (server di destinazione)

5.1 Aggiungere un host

  1. Infrastructure → Hosts → New host.
  2. Compilare: Name (identificativo breve, es. prod-app-01), Hostname (FQDN), eventuale IP (se indicato, SSH si collega all'IP), SSH username (utente dedicato, es. scarlet), porta, Environment, Runtime (PODMAN consigliato; NONE se non si sa ancora: si scoprirà con Discover).
  3. Facoltativo: gruppi di host, percorso base remoto (default /opt/scarlet), descrizione.
  4. Salvare. L'host compare con stato UNKNOWN.

La pagina del nuovo host elenca i passi successivi: aggiungere la credenziale, approvare il fingerprint, testare la connessione, eseguire Discover.

5.2 Preparare il server

Sul server di destinazione deve esistere un utente Linux dedicato (senza privilegi speciali) con accesso in scrittura al percorso base e con installati il runtime (podman/docker/kubectl) e gli strumenti tar, gzip, curl, nc. I comandi esatti sono mostrati nella pagina Security → Credentials e in docs/ssh.md. Per Podman rootless abilitare il "linger" dell'utente (loginctl enable-linger scarlet) così i container restano attivi dopo la disconnessione.

5.3 Modificare, disabilitare, eliminare

Dalla pagina dell'host: Edit (matita), Disable (l'host viene escluso da deployment, operazioni e riconciliazione senza toccare le applicazioni in esecuzione), Delete (solo se non ha storico di deployment; altrimenti va disabilitato per conservare la tracciabilità). Su PROD le azioni distruttive richiedono motivo e conferma digitata.

9. Credenziali SSH

Security → Credentials elenca per ogni host le credenziali attive e storiche. Con Add / rotate si inserisce:

  • Chiave privata SSH (consigliata, formato OpenSSH o PEM, preferibilmente ed25519) ed eventuale passphrase;
  • Password SSH (sconsigliata, utile solo per il primo accesso);
  • kubeconfig (solo per host Kubernetes in modalità API).

Il segreto è cifrato immediatamente con la chiave di cifratura dell'applicazione e non viene mai più mostrato, né nelle pagine, né nell'API, né nei log o nell'audit. Aggiungere una nuova credenziale disattiva la precedente (rotazione), che resta in elenco come INACTIVE. Revoke disattiva la credenziale corrente: l'host non sarà raggiungibile finché non se ne aggiunge una nuova.

Non riutilizzare per SCARLET chiavi usate da persone. Se una credenziale è compromessa: revocarla, rimuovere la chiave pubblica dai server, generarne una nuova e controllare l'audit (RUNBOOK §30).

10. Approvazione del fingerprint SSH

Per evitare attacchi "man-in-the-middle", SCARLET non si fida automaticamente della chiave pubblica del server. La prima volta (o quando la chiave cambia) la connessione viene bloccata e il fingerprint viene registrato come PENDING APPROVAL.

  1. Nella pagina dell'host premere Scan host key (o Test connection).
  2. Leggere il fingerprint reale sul server tramite un canale indipendente (console: ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub) e confrontarlo carattere per carattere con quello mostrato.
  3. Premere Approve fingerprint e digitare il fingerprint nella finestra di conferma.

Se lo stato è MISMATCH significa che il server presenta una chiave diversa da quella approvata: potrebbe essere stato reinstallato oppure qualcuno sta intercettando la connessione. Non approvare finché non si è verificato con il responsabile del server; l'evento è registrato in Audit → Security Events con gravità CRITICAL.

11. Test connessione e Discover

Test connection verifica che SCARLET riesca a collegarsi con la credenziale e la chiave approvata: mostra l'utente remoto e il tempo di risposta e imposta lo stato dell'host a ONLINE o OFFLINE.

Discover legge, senza modificare nulla, sistema operativo, kernel, CPU, memoria, disco, modalità SELinux e i runtime installati (Podman/Docker/Kubernetes con versione e modalità rootless). Se il runtime dell'host era NONE, il risultato suggerisce quello rilevato: modificare l'host per impostarlo. Refresh status ripete il solo test di connessione.

Le operazioni sono eseguite in background: una finestra mostra l'avanzamento e il risultato; il dettaglio completo (comandi eseguiti, output) è in Operations.

12. Gruppi di host e ambienti

Host Groups (es. PROD-API) raggruppano host dello stesso ambiente per selezionarli in blocco nel wizard di deployment e per limitare a quali gruppi un'applicazione può essere distribuita.

Environments mostra DEV e PROD con le regole: richiesta di conferma digitata, approvazione a due persone, rollback consentito, numero massimo di deployment in parallelo. Per PROD vale sempre la regola più restrittiva tra quella dell'ambiente e le impostazioni globali.

13. Applicazioni

Applications → New application. Il Code (es. customer-api, minuscole e trattini) deve coincidere con il campo application del manifest dei pacchetti e non è modificabile una volta pubblicate delle versioni. Si impostano:

  • Runtime principale e runtime aggiuntivi consentiti (es. un pacchetto Podman eseguibile anche su host Docker);
  • Ambienti e gruppi di host consentiti (vuoto = nessuna restrizione);
  • Health check predefinito (tipo, percorso, porta, stato atteso, timeout, tentativi) usato quando il manifest non lo specifica;
  • Allow hooks: consente ai pacchetti di eseguire script (scripts/*.sh) sul server prima/dopo il deployment. Da abilitare solo per pipeline di rilascio fidate.

La pagina di dettaglio mostra le versioni (con manifest e verifica di integrità dell'artefatto), le istanze con stato desiderato/reale/health/drift e i pulsanti di azione, e lo storico dei deployment. Da qui si avvia il wizard di deployment con l'applicazione preselezionata.

14. Pacchetti di rilascio

Un pacchetto è un archivio nome-versione.scarlet.tar.gz prodotto dal team di sviluppo, tipicamente con lo strumento scripts/build-scarlet-package.py. Contiene:

customer-api-2.5.0.scarlet.tar.gz
├── manifest.yaml        obbligatorio: applicazione, versione, runtime, immagine, porte, health check…
├── application/         file dell'applicazione o archivio immagine per host senza accesso al registry
├── config/              file di variabili d'ambiente non segrete
├── scripts/             script hook (pre-deploy, migrate, post-deploy)
├── docker-compose.yml   opzionale (modalità compose)
└── kubernetes/          manifest YAML per il runtime Kubernetes

SCARLET verifica estensione, integrità dell'archivio, assenza di percorsi pericolosi (es. ../), link e file speciali, dimensione, schema del manifest, esistenza dell'applicazione, compatibilità del runtime, univocità della versione e file richiesti. Il contenuto non viene mai eseguito sul server SCARLET.

Le Releases elencano tutte le versioni pubblicate con checksum SHA-256; una versione può essere disattivata (non più distribuibile) ma non cancellata né modificata.

15. Caricamento di un pacchetto

  1. Applications → Packages → Upload.
  2. Trascinare il file nell'area tratteggiata o cliccare per sceglierlo. Viene mostrato il checksum calcolato localmente.
  3. Facoltativo: selezionare l'applicazione per un controllo incrociato e inserire note di rilascio. Lasciare attivo "Create the release automatically".
  4. Premere Upload & validate. La barra mostra il trasferimento; al termine compare il risultato VALID o INVALID con l'elenco completo degli errori e degli avvisi.
  5. Se valido, la release è creata e il pulsante Deploy this release apre il wizard.

Errori tipici: applicazione non registrata (crearla o correggere il manifest), versione già esistente con contenuto diverso (pubblicare una nuova versione), hook presenti ma non abilitati sull'applicazione, file troppo grande (limite in Impostazioni). I pacchetti INVALID possono essere rivalidati o eliminati.

16. Configurazione e segreti

Applications → applicazione → Configuration, una scheda per ambiente (DEV, PROD). Ogni voce è una variabile d'ambiente consegnata all'applicazione al momento del deployment:

  • CONFIG: valore visibile (es. LOG_LEVEL=info);
  • SECRET: valore cifrato, visibile solo al momento dell'inserimento, mai più mostrato (es. DB_PASSWORD). Per cambiarlo si inserisce un nuovo valore; lasciando vuoto il campo si mantiene quello esistente.

Le voci qui definite prevalgono sui valori predefiniti del manifest. I segreti dichiarati dal pacchetto (secrets:) devono essere configurati prima del deployment, altrimenti il pre-flight fallisce. Ogni modifica crea una nuova versione della configurazione (elenco a destra) ed è registrata in audit senza i valori dei segreti. In PROD la modifica richiede permesso PROD e motivo.

17. Deployment guidato (wizard)

Operations → Deployments → New deployment (o Deploy dalla pagina dell'applicazione o dell'host). Il wizard ha nove passi:

  1. Application: scegliere l'applicazione.
  2. Version: scegliere la release (solo versioni attive con pacchetto valido).
  3. Targets: uno o più host; quelli incompatibili sono in grigio con il motivo (ambiente non consentito, runtime diverso, host disabilitato…). Il menu "Quick select host group" seleziona un intero gruppo.
  4. Environment: riepilogo degli ambienti coinvolti; strategia SEQUENTIAL (un host per volta, si ferma al primo errore) o PARALLEL (fino al limite configurato); rollback automatico (sì/no/predefinito).
  5. Pre-flight: controlli automatici su ogni host — connettività SSH, chiave approvata, credenziale, runtime installato, spazio disco, memoria, porte libere, integrità del pacchetto, segreti configurati, assenza di operazioni in conflitto, limite di parallelismo. Con esiti FAIL non si può proseguire: correggere e premere "Re-run checks".
  6. Confirmation: riepilogo, campo Reason (obbligatorio in PROD, consigliato sempre: es. numero di change) e, per PROD, la frase da digitare ({{ prod_phrase }}).
  7. Execution: elenco dei passi aggiornato in tempo reale (validazione, trasferimento, verifica checksum, estrazione, configurazione, hook, installazione, attivazione, avvio).
  8. Health check: esito della verifica di salute con i tentativi effettuati.
  9. Result: SUCCESS con la versione distribuita, oppure gli errori per host con link al dettaglio.

Il dettaglio del deployment (Deployments → riferimento DEP-…) mostra riepilogo, approvazioni, pre-flight, ogni passo con durata e output dei comandi remoti, timeline e piano. Il log completo si scarica con Download log. I deployment in coda o in attesa di approvazione si possono annullare.

14.1 Cosa succede sul server

SCARLET crea la struttura /opt/scarlet/applications/<app>/ con releases/<versione> (release immutabili), current (link alla release attiva, cambiato in modo atomico), shared/ (configurazione, dati e log persistenti tra le versioni), staging/ e backups/. La release precedente non viene cancellata: è il candidato per il rollback.

18. Operazioni in PRODUZIONE

Gli host PROD sono contrassegnati dal badge rosso PROD e da un banner nelle pagine di dettaglio. Per ogni operazione che modifica un sistema di produzione (deploy, stop, restart, rollback, cancellazione, modifica configurazione) servono:

  • il permesso prod.* corrispondente (ruoli PROD_OPERATOR o ADMIN);
  • un motivo (registrato nell'audit);
  • la frase di conferma digitata esattamente: {{ prod_phrase }} per il deployment, STOP PROD, RESTART PROD, ROLLBACK PROD, DELETE PROD per le altre;
  • se abilitata, l'approvazione di un secondo utente.

In PROD il numero di deployment paralleli è limitato (predefinito 1). Le operazioni di sola lettura (status, health, log) non richiedono conferma.

19. Approvazione a due persone

Se l'ambiente o l'impostazione globale richiede l'approvazione, il deployment PROD resta in stato PENDING APPROVAL e gli utenti con permesso di approvazione ricevono una notifica. Nel dettaglio del deployment un utente diverso dal richiedente preme Approve (digitando APPROVE e un commento) oppure Reject. All'approvazione l'esecuzione parte subito; richiedente, approvatore e commento restano nell'audit.

20. Start, Stop, Restart, Status

Dalla riga dell'istanza (pagina applicazione, pagina host o Monitoring → Health):

StatusInterroga il runtime: stato del container/deployment, versione in esecuzione, dettagli tecnici e verdetto di drift. Nessuna conferma.
StartAvvia la versione desiderata. Se già in esecuzione restituisce ALREADY_RUNNING. Imposta lo stato desiderato a RUNNING.
StopArresta l'applicazione (attesa graduale, poi terminazione forzata). Se già ferma: ALREADY_STOPPED. Imposta lo stato desiderato a STOPPED (nessun drift per un arresto voluto).
RestartRiavvia sempre l'applicazione.
HealthEsegue il controllo di salute configurato e aggiorna lo stato.
LogsRecupera le ultime righe di log dal runtime (vedi il capitolo Consultare i log).
RollbackTorna alla release precedente (vedi il capitolo Rollback).

Ogni operazione apre una finestra che segue l'esecuzione in tempo reale e mostra il risultato e i comandi eseguiti. Due operazioni sullo stesso host/applicazione non possono sovrapporsi: la seconda viene rifiutata con "Another operation is already running".

21. Consultare i log

Monitoring → Logs: scegliere l'istanza (applicazione @ host), il numero di righe (100–5000), l'intervallo (ultimi 10 minuti, 1 ora…), un testo da cercare, poi Fetch. Le righe con "error" sono evidenziate in rosso, i "warning" in giallo, il testo cercato è marcato. Auto-refresh aggiorna ogni 10 secondi; Download salva il risultato. I log provengono esclusivamente dal runtime (podman logs, docker logs, kubectl logs): non è possibile leggere file arbitrari del server.

22. Health check

Il tipo di controllo è definito dal manifest del pacchetto (o dai valori predefiniti dell'applicazione): HTTP/HTTPS (richiesta a un percorso con stato atteso), TCP (porta aperta), COMMAND (comando dentro il container), CONTAINER_STATUS (container in esecuzione), KUBERNETES_STATUS (repliche pronte). Il controllo è eseguito sul server di destinazione, con tentativi e intervallo configurati. Viene eseguito alla fine di ogni deployment, su richiesta e automaticamente ogni 10 minuti per le istanze in esecuzione.

Monitoring → Health mostra tutte le istanze con stato reale, salute, ultimo controllo, messaggio e drift; Check all running mette in coda un controllo per tutte. Il primo passaggio a UNHEALTHY genera una notifica e un evento di audit.

23. Rollback

Dal pulsante Rollback dell'istanza (o dal dettaglio di un deployment fallito dopo l'attivazione). La finestra indica la versione corrente e quella di destinazione (la precedente riuscita). Serve un motivo e, in PROD, la frase ROLLBACK PROD. SCARLET riattiva la release precedente già presente sul server, riavvia l'applicazione, esegue gli hook di rollback e l'health check, e aggiorna la versione corrente. La release sostituita non viene cancellata e diventa a sua volta il nuovo candidato di rollback.

Se è attivo il rollback automatico, un deployment che fallisce dopo l'attivazione (avvio o health check) torna da solo alla versione precedente e termina con stato ROLLED BACK; altrimenti termina con ROLLBACK REQUIRED e mostra il pulsante di rollback manuale.

24. Stato desiderato, stato reale e drift

Per ogni istanza SCARLET conserva due informazioni: lo stato desiderato (versione e RUNNING/STOPPED richiesti dall'operatore tramite deployment e operazioni) e lo stato reale osservato sul server. Il processo di riconciliazione confronta periodicamente le due cose (ogni 5 minuti per impostazione predefinita, o su richiesta con Reconcile nella pagina host) e segnala il drift:

VERSIONsul server gira una versione diversa da quella desiderata (es. qualcuno ha modificato il container a mano)
UNEXPECTED_STOPl'applicazione dovrebbe essere in esecuzione ma è ferma o in errore
STATEdovrebbe essere ferma ma è in esecuzione, oppure numero di repliche diverso
MISSINGnessun container e nessuna release installata
RUNTIMEil runtime dell'host è cambiato

Il drift è evidenziato in dashboard, in Monitoring → Health e nella pagina dell'applicazione. Per risolverlo: rieseguire il deployment della versione corretta oppure usare Start/Stop. Solo in DEV, e solo se l'amministratore lo abilita, la riconciliazione può riallineare da sola lo stato (riavviando un container fermo).

25. Operazioni e job

Operations → Lifecycle Operations elenca ogni operazione con tipo, applicazione, host, esito, richiedente, durata; il dettaglio mostra il risultato e il registro dei comandi eseguiti sul server (comando, codice di uscita, output). Jobs mostra ciò che è in corso adesso (operazioni e deployment) e permette di cercare un job per identificativo. Le operazioni in coda si possono annullare.

Ogni operazione ha un riferimento leggibile (OP-20260911-000123, DEP-…, RBK-…) e un request id (visibile nel piè di pagina e negli errori) che collega quanto vedete nel browser ai log del server: citatelo quando chiedete assistenza.

26. Audit e eventi di sicurezza

Audit → Audit Log: registro immutabile di ogni azione (login, creazione/modifica host, cambio credenziali, approvazione fingerprint, caricamenti, deployment avviati/completati/falliti, start/stop/restart, rollback, health check falliti, modifiche di configurazione e impostazioni) con utente, IP, esito, entità coinvolte e dettagli (senza segreti). Filtri per utente, azione, entità, ambiente, esito e data; ricerca testuale; esportazione CSV/JSON per chi ha il permesso.

Audit → Security Events: eventi rilevanti per la sicurezza (fingerprint SSH cambiato, account bloccato, checksum di un artefatto non corrispondente). Gli amministratori possono prenderli in carico (acknowledge).

27. Notifiche

La campanella in alto mostra le notifiche non lette: deployment riusciti o falliti, rollback, health check falliti, host non raggiungibile, drift rilevato, richieste di approvazione. La pagina Notifications (dal menu a tendina) le elenca tutte e permette di segnarle come lette. Se l'amministratore ha configurato il server di posta, gli eventi critici vengono inviati anche via e-mail.

28. Utenti, ruoli e token API

Security → Users (solo ADMIN): creazione utenti con password iniziale (da cambiare al primo accesso), assegnazione ruoli, attivazione/disattivazione, sblocco, reset password, eliminazione (non si può eliminare l'ultimo amministratore né sé stessi). Security → Roles: ruoli di sistema e ruoli personalizzati con permessi granulari; i permessi prod.* sono evidenziati in rosso.

Token API (menu utente → API tokens): token personali per script e pipeline (es. caricamento automatico dei pacchetti). Il token viene mostrato una sola volta al momento della creazione; ha una scadenza e può essere revocato. Eredita i permessi dell'utente e le sue azioni finiscono nell'audit con il nome dell'utente.

29. Impostazioni di sistema

System → Settings (solo ADMIN) permette di modificare a caldo, senza riavvio: timeout SSH e di deployment, parametri predefiniti dell'health check, limite di caricamento, politiche di conservazione (release, log, health check), controlli di produzione (conferma, approvazione, rollback, motivo, frase), rollback automatico, parallelismo, riconciliazione. Ogni modifica è registrata in audit. Le impostazioni non contengono mai segreti.

30. Uso dell'API

Tutto ciò che fa l'interfaccia è disponibile come API REST JSON documentata in System → API Docs (Swagger). Esempio di caricamento pacchetto da una pipeline con un token:

curl -H "Authorization: Bearer scl_…" \
     -F file=@dist/customer-api-2.5.0.scarlet.tar.gz \
     https://scarlet.example.internal/api/packages/upload

Le operazioni asincrone rispondono 202 Accepted con l'indirizzo da interrogare (meta.poll) per seguire l'avanzamento. Le operazioni in PROD richiedono nel corpo JSON i campi reason e confirmation.

33. Buone pratiche

  • Provare sempre una nuova versione in DEV prima di portarla in PROD.
  • Indicare sempre un motivo significativo (numero di change, ticket): finisce nell'audit e aiuta chi verrà dopo.
  • Non modificare mai a mano container o file gestiti da SCARLET sui server: si genera drift e si perde la tracciabilità.
  • Verificare i fingerprint SSH tramite un canale indipendente; non approvare mai "per far funzionare".
  • Usare chiavi SSH dedicate a SCARLET, ruotarle periodicamente e revocarle subito in caso di dubbio.
  • Configurare i segreti in SCARLET, mai dentro i pacchetti.
  • Tenere le release recenti sui server (retention) per poter fare rollback rapidi.
  • Controllare regolarmente Dashboard e Monitoring → Health: drift e health check falliti vanno gestiti, non ignorati.
