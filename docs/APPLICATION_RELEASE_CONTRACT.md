# SCARLET Application Release Contract (v1)

This document is the formal, versioned contract between **application development teams** and
**operations**. A team that follows it can produce releases that SCARLET validates, deploys,
monitors and rolls back — without knowing anything about SCARLET's internals.

Contract version: **manifest_version 1**. Breaking changes will bump the version; SCARLET keeps
accepting older versions listed in its "supported manifest versions".

---

## 1. Package structure

A release is a single gzip-compressed tar archive named

```
<application>-<version>.scarlet.tar.gz        e.g. customer-api-2.5.0.scarlet.tar.gz
```

with this layout (paths relative to the archive root, no leading `./`):

```
manifest.yaml            REQUIRED  release descriptor (this contract)
application/             optional  payload: image archive, binaries, static files
config/                  optional  non-secret environment files referenced by environment_files
scripts/                 optional  hook scripts (*.sh) referenced by hooks
docker-compose.yml       optional  compose mode (docker/podman)
Containerfile|Dockerfile optional  informational only (SCARLET never builds images on targets)
kubernetes/              optional  Kubernetes YAML manifests (Deployment, Service, ConfigMap, Secret, Namespace)
helm/                    optional  Helm chart (reserved; validated for presence only)
checksums.sha256         generated by the builder
README.md, CHANGELOG.md, LICENSE   optional
```

Rules enforced by the validator:
- only regular files and directories; **no symlinks, hard links, devices, setuid/setgid bits**;
- no absolute paths, no `..`, no Windows drive letters; member names use `[A-Za-z0-9._-]`;
- at most 20 000 members and 8 GiB uncompressed (configurable by operations);
- unknown top-level entries produce a warning, not an error;
- `manifest.yaml` ≤ 256 KiB, UTF-8, a YAML mapping.

Build with the reference tool (validates the result):

```bash
python scripts/build-scarlet-package.py --source ./my-app --version 2.5.0 --output dist/
```

`--version` overrides `version` and fills `image.tag` when it is empty/placeholder, so one source
tree produces successive releases.

## 2. Manifest format

```yaml
manifest_version: 1                 # integer, required
application: customer-api           # required, lowercase, digits, single dashes; must match the SCARLET application code
version: 2.5.0                      # required, semantic version (see §3)
runtime: podman                     # required: docker | podman | kubernetes
description: Customer master data API

image:                              # required for docker/podman unless compose is used
  name: registry.example.internal/team/customer-api   # [registry[:port]/]path, lowercase
  tag: 2.5.0                        # tag; pin it — never "latest" in production
  archive: application/image.tar    # optional: `podman save` archive for air-gapped hosts
  pull_policy: if-not-present       # if-not-present | always | never (never requires archive)

ports:
  - container: 8080                 # 1-65535
    host: 8080                      # optional, defaults to container
    protocol: tcp                   # tcp | udp
    bind: 127.0.0.1                 # optional host interface

environment:                        # non-secret defaults, KEY: value (KEY = [A-Z_][A-Z0-9_]*, SCARLET_* reserved)
  LOG_LEVEL: info
environment_files:                  # files inside the package merged into the environment
  - config/app.env
secrets:                            # names that MUST be configured in SCARLET as SECRET before deploying
  - DB_PASSWORD

volumes:
  - name: data                      # subdirectory of the shared area
    mount: /var/lib/app/data        # absolute path inside the container
    shared: data                    # data | config | logs  (persist across releases)
    read_only: false

healthcheck:
  type: http                        # http | https | tcp | command | container_status | kubernetes_status
  path: /health                     # http(s)
  port: 8080                        # defaults to the first published host port
  expected_status: 200
  timeout: 5                        # seconds per probe
  retries: 5
  interval: 3                       # seconds between retries
  command: /app/healthcheck.sh      # type command: executed inside the container (no shell metacharacters)

deployment:
  strategy: recreate                # recreate | rolling (rolling applies to kubernetes)
  start_timeout: 120
  stop_timeout: 60
  stop_grace_period: 10             # seconds before SIGKILL
  restart_policy: unless-stopped    # always | unless-stopped | on-failure | no
  replicas: 1                       # kubernetes replicas
  user: "1000:1000"                 # container user (numeric)
  read_only_rootfs: false

resources:
  cpu: "1"                          # "0.5", "500m", "2"
  memory: 512Mi                     # Ki | Mi | Gi

hooks:                              # executed on the target host, only if operations enabled hooks for the application
  pre_deploy:  [scripts/pre-deploy.sh]
  migrate:     [scripts/migrate.sh]
  post_deploy: [scripts/post-deploy.sh]
  pre_rollback: []
  post_rollback: []
  timeout: 300                      # seconds per script

dependencies:                       # informational, shown to operators
  - name: postgres
    type: database                  # service | database | queue | application | other
    required: true
    description: PostgreSQL 15+

kubernetes:                         # required when runtime: kubernetes
  namespace: customer               # optional override of the host namespace
  manifests: kubernetes             # directory with YAML manifests
  deployment_name: customer-api     # Deployment to watch (default: application code)
  container_name: app
  service: { type: ClusterIP, port: 80, target_port: 8080 }
  helm: { chart: helm/customer-api, values: [helm/values.yaml] }   # reserved

compose:                            # alternative to image for docker/podman
  file: docker-compose.yml
  project_name: customer-api

rollback:
  enabled: true
  keep_releases: 5

metadata:                           # free key/value (max 32)
  team: customer
```

Unknown keys are **rejected** (strict schema). Every value that may reach a remote command is
validated against an allow-list (image names, tags, paths, ports, env keys).

## 3. Semantic versioning

`MAJOR.MINOR.PATCH[-prerelease][+build]` (SemVer 2.0). Ordering follows SemVer. SCARLET stores
major/minor/patch/prerelease/build separately and the original string. **Versions are immutable**:
uploading a different package with an existing version is refused; publish a new version.

## 4. Runtime declaration

| runtime | how SCARLET runs it |
|---|---|
| `podman` | `podman run -d --name <app> --label scarlet.* --env-file <shared>/config/scarlet.env -p … -v …:Z --restart … image:tag`; or `podman compose` in compose mode |
| `docker` | same with `docker`; volumes without SELinux relabel |
| `kubernetes` | applies the YAML in `kubernetes/` to the namespace (kubectl over SSH, or the API when a kubeconfig is attached to the host), labels objects with `scarlet.io/application` and `scarlet.io/version`, waits for rollout |

The application's SCARLET record limits which runtimes/environments/host groups a package may
target; a `podman` package can run on a `docker` host only if the application allows it.

## 5. Ports

`ports` are published `host:container/protocol`. Pre-flight checks that host ports are free
(unless used by the current release of the same application). Duplicate host ports are rejected.
Rootless Podman cannot bind ports < 1024 unless the host is configured for it.

## 6. Environment variables and configuration

Precedence (lowest → highest):
1. `environment` in the manifest;
2. `environment_files` shipped in the package (KEY=value lines);
3. **SCARLET configuration** for the application and environment (Applications → Configuration):
   CONFIG entries (visible) and SECRET entries (encrypted, write-only);
4. SCARLET-provided variables: `SCARLET_APPLICATION`, `SCARLET_VERSION`, `SCARLET_ENVIRONMENT`,
   `SCARLET_RELEASE_DIR`, `SCARLET_SHARED_DIR`, `SCARLET_DEPLOYMENT`.

Everything is rendered to `<base>/applications/<app>/shared/config/scarlet.env` on the target and
passed with `--env-file`. Values are single-line. The env file is readable only by the SSH user.

## 7. Secrets

Declare the names in `secrets:`. Pre-flight **fails** when a declared secret is not configured.
Never put secret values in the package, in `environment`, or in Kubernetes Secret manifests in
clear text; use SCARLET SECRET entries (Docker/Podman) or a cluster secret manager (Kubernetes).

## 8. Health checks

The deployment is SUCCESS only when the health check passes within `retries × (timeout +
interval)`. Probes run **on the target host**: `http`/`tcp` probe `127.0.0.1:<host port>`;
`command` runs inside the container; `container_status` requires state `running` (and a healthy
Docker/Podman `HEALTHCHECK` if the image defines one); `kubernetes_status` requires
`readyReplicas == replicas`. Periodic sweeps re-run the same probe.

## 9. Resource requirements

`resources.cpu/memory` become `--cpus/--memory` (Docker/Podman) and are compared with the host's
available memory during pre-flight (warning). For Kubernetes set requests/limits in the manifests.

## 10. Startup behaviour

- The image must start without interactive input and keep a foreground process.
- Expose readiness through the health check; SCARLET waits up to `start_timeout`.
- Listen on the container port declared in `ports`.
- Read configuration from environment variables (12-factor).

## 11. Shutdown behaviour

- Handle `SIGTERM` and exit within `stop_grace_period`; afterwards the runtime sends `SIGKILL`.
- Persist state only under `volumes` mounts (shared area) — the release directory is immutable and
  replaced on every deployment.

## 12. Rollback behaviour

SCARLET keeps previous releases under `releases/<version>` and switches the `current` symlink
atomically. Rollback re-activates the previous release, re-runs `pre_rollback`/`post_rollback`
hooks and the health check. Requirements for the application:
- schema changes must be backward compatible for at least one version (expand/contract), or the
  `migrate` hook must be reversible;
- data written by version N+1 must not break version N.

## 13. Dependencies

`dependencies` is informational and displayed to operators during deployment. SCARLET does not
provision databases or queues.

## 14. Hooks (migration, pre/post deployment)

Hooks are POSIX `sh` scripts under `scripts/`, executed **on the target host** as the SSH user,
with `sh -e` under `timeout <hooks.timeout>`, working directory unspecified — always use the
`SCARLET_*` variables for paths. Order in a deployment:

```
validate → pre-flight → transfer → verify → extract → configure(env file)
→ pre_deploy → migrate → install(image) → activate(current symlink) → start → health
→ post_deploy (non-critical) → finalize → cleanup
```

Rollback: `pre_rollback → activate previous → start → health → post_rollback`.

Rules: hooks must be **idempotent** (they run on every deployment), must not prompt, must exit
non-zero on failure (which aborts the deployment before activation), must not modify anything
outside the application's directories or its own database. Operations must explicitly enable
hooks per application (`allow_hooks`); packages with hooks are otherwise rejected at upload.

## 15. Examples

`examples/podman-app` (single container, hooks, secrets), `examples/docker-app` (compose mode),
`examples/kubernetes-app` (Deployment + Service + ConfigMap). Each builds into a valid package with
`scripts/build-scarlet-package.py`.

## 16. Checklist before handing a release to operations

- [ ] `application` matches the SCARLET application code; `version` is new and SemVer.
- [ ] `image.tag` is pinned and the image is pushed to a registry the target can reach (or `image.archive` is included).
- [ ] all secrets are declared in `secrets:` and communicated to operations for configuration.
- [ ] health check works against a locally started container (`curl http://127.0.0.1:<port><path>`).
- [ ] hooks are idempotent and tested; `allow_hooks` requested from operations.
- [ ] `python scripts/build-scarlet-package.py …` reports no errors.
